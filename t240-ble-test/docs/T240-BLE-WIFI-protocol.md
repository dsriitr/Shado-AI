# 一、普遍约定：

## 1、crc算法

```c
u16 crc16_compute(u8 const * p_data, u32 size, u16 const * p_crc)
{
    u16 crc = (p_crc == NULL) ? 0xFFFF : *p_crc;

    for (u32 i = 0; i < size; i++)
    {
        crc  = (u8)(crc >> 8) | (crc << 8);
        crc ^= p_data[i];
        crc ^= (u8)(crc & 0xFF) >> 4;
        crc ^= (crc << 8) << 4;
        crc ^= ((crc & 0xFF) << 4) << 1;
    }

    return crc;
}
```

| 说明   |                                                            |

# 二、协议普通指令

## 1、握手加配对绑定

​	app与设备各自绑定对方，连接时双方都需要校验通过，方可保持连接，否则app或设备主动断开连接。

约定，传输握手指令过程中，使用1Byte表征 步骤，放在指令后（wifi密码使用设备UUID前8Bytes）

​	1) app连接上设备之后，app下发notify打开数据传送通道   设备端响应并发送设备UUID

```
指令值：0x01 0x00
命令格式：0x01 0x01 0x00

device->app: 0x01 0x01 0x00 0x00 json数据

json数据样例：
{
	"uuid":	"623d289d-0a37-5260-b0f1-976e9bc9ea4e",   // 设备UUID，wifi密码为"623d289d"
}
```

​	2) app校验设备UUID，当设备上报的设备UUID存在于app已连接过设备列表中，或者设备列表无此UUID，表示设备已连接过或初次连接，app缓存该UUID，等待设备端校验app UUID；若app不想连接该设备，则app主动断连，无需下发指令。（app可有多台设备连接过）

​		app下发app UUID，等待设备端校验app UUID

```
指令值：0x01 0x00
命令格式：0x01 0x01 0x00
app->device: 0x01 0x01 0x00 0x01 json数据

json数据样例：
{
	"time": 1730254726, // 时间戳
	"uuid":	"xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",   // app UUID
}
```

 	3) 设备端接收到app UUID后，校验该UUID。当设备端未连接过app时，存储app UUID并返回状态；当设备端已连接过app时，与本地存储的已连接过的app的UUID做比较，相同则表示是绑定设备，可以保持连接，否则表示非绑定设备，设备返回断连信息，主动断连，断连信息见下表。（设备只能绑一个app）

```
指令值：0x01 0x00
命令格式：0x01 0x01 0x00

device->app: 0x01 0x01 0x00 0x02 0xxx json数据 // 当0xxx为0x00时，才能附带json数据，否则不附带

json数据样例：
{
	"name":  "T240(BLE)", // 设备名称
	"SN":	"352401241100999", // 由客户确定的唯一SN码
	"uuid":	"623d289d-0a37-5260-b0f1-976e9bc9ea4e",   // 设备UUID
	"brand":	"升迈",  // 品牌
	"model":	"Record Card",  // 产品型号
	"deviceVerson":    "2024-06-06",  // 设备版本
	"isAudioRecorded": "1",    // 是否有音频在录音  这个就是判断在未连接设备之前  设备是否正在录音  0:未录音  1:正在录音
	"screen":	"yes", // yes 表示机器有屏幕，no 表示机器没有屏幕
	"WifiSsid":     "M2(045107968c78)" // xx(xxxxxxxxxxxx)，括号外是型号，例如M2，括号内是随机字符(数字和字母，12个)
}
```

| 码值 （0xxx） |                             说明                             |
| :-----------: | :----------------------------------------------------------: |
|     0x00      |                       验证成功可以连接                       |
|     0x01      |                      app UUID 校验失败                       |
|     0x02      |              数据长度校验失败（长度 > 4Bytes）               |
|     0x03      |                    未握手直接发送其他指令                    |
|     0x04      | 握手超时（从连接上开始计时，5s内未完成握手，即视为错误设备。<br />需要notify开启后出现此情况，才能发送完成，否则现象为直接断开，不会有返回值） |

## 22、打开WIFI

​	打开WIFI后，SD卡控制权移交到WIFI芯片，此时U盘功能将被屏蔽。WiFi打开后，本地音频同步数据和OTA数据走WIFI，实时录音音频和控制命令依旧走ble。返回指令跟随 1Byte 失败码，以一位代表一种失败原因，多原因导致失败将以位或形式组织失败码。

```
指令值：0x0A 0x00
命令格式：0x01 0x0A 0x00 

例：
app->device: 0x01 0x0A 0x00 
device->app: 0x01 0x0A 0x00 0xxx 
```

| 0xxx  | 意义                        |
| ----- | --------------------------- |
| 0x00  | WIFI打开成功                |
| bit 0 | 设备繁忙（701正在访问SD卡） |

WIFI通道信息如下：

```
设备端：
1）	角色：server
2）	WIFI模式：AP
3）	SSID：T240(WIFI)
4）	Password：设备端UUID前8Bytes
5）	通信方式：TCP socket
6）	IP：192.168.1.1
7）	掩码：255.255.255.0
8）	端口号：32769
9）	单帧最大用户数据长度：ota数据40KB/帧，音频数据1KB/帧

手机端：
1）	角色：client
```

# 三、协议音频同步指令

​	音频同步分为**wifi同步**和**ble同步**，其中wifi同步只能同步本地音频，ble同步可以本地同步或实时录音同步



## 1、ble实时音频同步

​	使用ble实时同步时，需要关闭wifi

### 1）app下发指令启动录音或设备按键启动录音

## 2、ble本地音频同步

​	使用ble本地同步时，需要关闭wifi

### 1）app通知设备开始同步本地音频

​	同步状态开启通知。app连接后，正式开始同步设备端音频前，先发送一次该指令，通知设备端接下来进入音频同步状态。全部文件同步结束后再发送一次该指令，通知设备端退出音频同步状态。置1为开始同步，置0为同步结束，开始同步后，设备端实体按键无效。如果在传输过程中想停止传输，则使用该命令并置0。

```
指令值：0x74 0x00
命令格式：0x01 0x74 0x00 0xxx

例：
app->device: 0x01 0x74 0x00 0xxx
device->app: 0x01 0x74 0x00 0xxx // 数据原样返回
```



### 2) app 获取设备端文件列表

​	设备端返回的文件信息以json格式组织。在发送实际文件json数据前，先发一帧文件数量。在没有完整接收完所有json数据前，不要同步音频，否则概率性无法完整发送文件json数据。如果当前正在扫盘，将返回设备繁忙指令，并且需要等待扫盘完成后才能进行文件同步。以及，其他任何带有回复的指令，在没有接收到回复之前，不要进行下一步操作。

```
指令值：0x1B 0x00
命令格式：0x01 0x1B 0x00 

app->device: 0x01 0x1B 0x00 
```

```

device->app: 0x01 0x1B 0x00 文件数量json // 返回文件数量
device->app: 0x01 0x1B 0x00 音频json // 本地有几条音频，就会返回几次json

// 文件数量json数据例子
{
	"FileNum":	300
}

// 音频json数据例子
{
	"file":	"R20200101-000013.opus",  // 文件名
	"size":	7680,					// Bytes
	"creat_time":	1577808013,		 // 文件创建的时间戳
	"duration_ms":	3,				// 音频持续时间，单位毫秒
	"type":	3,						// 设备端使用，app可不用理会
	"index":	4,					// 第4个文件
	"delete":	0,					// 设备端使用，app可不用理会
	"toggle_switch":	0 			 // 拨码开关状态
}
```

```
// 设备繁忙时，返回错误信息json
device->app: 0x01 0x1B 0x00 错误信息json

// json例：
{
	"AudioFileList":	"MemoryBusy"
}
```



### 3）app下发同步音频指令

```

命令格式：0x01 0x1C 0x00 

// 例如，同步 R20200101-000013.opus
app->device: 0x01 0x1C 0x00 "R20200101-000013.opus"
```

​	设备端收到命令和文件名后，开始返回音频数据。格式见第一章第二节，cmd为 0x1C 0x00 。 

​	如果设备在扫盘中，app下发同步音频指令，则设备返回json繁忙标志。

```
// json例：
{
        "AudioFileSync":        "MemoryBusy"
}

app->device: 0x01 0x1C 0x00 json
```

​	当前文件数据发送完成后，设备端返回同步停止命令以及整个文件的crc

```
指令值：0x1D 0x00

device->app: 0x01 0x1D 0x00 crcL crcH
```

## 3、wifi同步本地音频

​	wifi同步本地音频和ble同步本地音频流程相似，只是数据填充格式不同。

​	wifi同步本地音频时，命令使用wifi数据填充格式，见第一章第3节。其中，命令、排序和CRC字段全部填0即可，且无需携带数据的命令，data字段不需要填，直接接续上CRC字段即可。

​	命令填在命令字段，命令附带的数据填在data字段。

​	wifi同步本地音频使用到的命令：

| 命令      | 解释           |
| --------- | -------------- |
| 0x74 0x00 | 见第三章2.1节  |
| 0x1B 0x00 | 见第三章2.2节  |
| 0x1C 0x00 | 见第三章2.3节  |
| 0x1D 0x00 | 见第三章2.3节  |
| 0x0B 0x00 | 见第二章第23节 |



流程如下：

### 		1) app下发打开wifi命令

​			app通过ble，下发打开wifi命令，连接wifi和socket。在socket连接成功之前，ble维持连接；socket连接成功后，设备端主动断开ble连接，仅维持wifi socket连接

### 		2)  socket连接成功后，app通知设备开始同步本地音频

​	同步状态开启通知。app连接后，正式开始同步设备端音频前，先发送一次该指令，通知设备端接下来进入音频同步状态。全部文件同步结束后再发送一次该指令，通知设备端退出音频同步状态。置1为开始同步，置0为同步结束。如果在传输过程中想停止传输，则使用该命令并置0。

​	发送该命令退出同步音频状态后，设别端开启一个13s的超时，13s内，没有收到关闭wifi指令，则自动关闭wifi开启ble

```
指令值：0x74 0x00

// 设备端收到后，原样返回该指令
```



### 		3）app下发获取文件列表指令

​			app通过socket，下发获取文件列表指令，设备端将返回json数据。与ble返回多个json不同的是，此处只返回1个json数据，数据组织格式为一个对象和一个对象数组

```c
// 例，一个对象和一个对象数组
{
	"FileNum":	2,
	"AudioFileArray":	[{
			"file":	"R20240101-000052.opus",
			"size":	25372160,
			"creat_time":	1704038452,
			"duration_ms":	12221,
			"type":	3,
			"index":	1,
			"delete":	0,
        	 "toggle_switch":	0 			 // 拨码开关状态
		}, {
			"file":	"R20241130-060007.opus",
			"size":	43195840,
			"creat_time":	1732917607,
			"duration_ms":	20807,
			"type":	3,
			"index":	2,
			"delete":	0,
        	 "toggle_switch":	0 			 // 拨码开关状态
		}]
}
```

### 		4) app下发需要同步的文件名

​			根据上一步获取到的json，app通过socket下发需要的文件的文件名，设备端以wifi数据填充格式返回本地音频文件数据，格式见第一章第3节。此步骤中，wifi数据格式所有的字段都会填写对应的信息。

​			当前文件的所有数据发送完成后，设备端返回发送完成指令，app端可以选择继续同步下一条音频或结束同步。

### 		5) app下发结束同步音频

​			app通过socket发送关闭wifi命令即可结束音频同步。关闭wifi后，设备自动开启ble，app需主动回连设备。



### 6）断点传输

​	在wifi音频同步过程中，app检测到当前连接的wifi不是设备的热点，意味着设备端传输已经失败重启，app需要重连热点并重连socket。

​	socket连接完成后，只需要发送该命令，设备端将从断点处返回音频，不需要再跑一次获取文件列表和发送文件名流程。

​	app下发该命令时，以json格式发送文件名和断点。设备端接收到该命令后，返回1byte结果，0x01, 成功读取断点，即将开始传输，0x00，断点读取失败，检查文件名或断点是否填写有误

```
指令值：0x78 0x00

例，R20250303-144723.opus传输中断，app下发json如下：
{
	"file":		"R20250303-144723.opus", // 字符串，需要断点传输的文件的文件名
	"index":	xxx		// 整数，第几帧中断（例如app完整接收了 index9 帧，则此处填 9，设备端将从 index10 开始返回数据）
	"crc":		xxx		// 整数，中断帧的crc（例如app完整接收了 index9 帧，则此处填 index9 的crc16值）
}

```



# 四、wifi ota

​	app通过ble，下发打开wifi命令，连接wifi和socket。在socket连接成功之前，ble维持连接；socket连接成功后，设备端主动断开ble连接，仅维持wifi socket连接。

​	如果wifi和socket多次连接仍然失败，app可通过ble发送关闭wifi指令。

​	连接上wifi和socket后，ota命令都通过socket发送接收，数据填充格式见第一章第3节。ota数据发送接收时，需要双方校验交互。设备端返回接收成功后，app方可推送下一帧。

​	app会预先拿到拿到两个 **.ufw** 文件，wifi ota实际上是将两个ufw文件发送给设备端。



## 1、app预先拿到的ufw文件

```
例：
ble芯片升级文件：update_xxx_ble_v12.4_0FC1-454BEF39_20241119.ufw
	说明：
	1、update：该文件为ota使用的文件
	2、xxx：项目名（例如 T240C）
	3、ble：该ota文件用于ble芯片的升级
	4、v12.4：版本
	5、0FC1-454BEF39：ota文件的唯一校验码
	6、20241119：文件创建日期

wifi芯片升级文件：update_xxx_wifi_v1.6_5CEA-52E35B42_20241119.ufw
	说明：
	1、update：该文件为ota使用的文件
	2、xxx：项目名（例如 T240C）
	3、wifi：该ota文件用于wifi芯片的升级
	4、v1.6：版本
	5、5CEA-52E35B42：ota文件的唯一校验码
	6、20241119：文件创建日期
```

​	

## 2、wifi ota指令列表

​	指令填充在数据格式中的 **命令** 字段。

| 命令               | 数值      | 说明                                                         |
| ------------------ | --------- | ------------------------------------------------------------ |
| OTA 开始           | 0xA0 0x00 | app 通知设备开始 OTA， 并且附带 OTA 相关信息。 <br/>设备检查当前条件，返回能否开始 OTA |
| OTA 数据包推送开始 | 0xA1 0x00 | 分为 ble 芯片数据包和 WiFi 芯片数据包                        |
| OTA 数据包         | 0xA2 0x00 | 当前芯片数据包推送                                           |
| OTA 数据包推送结束 | 0xA3 0x00 | 当前芯片数据包推送完成                                       |
| OTA 进度           | 0xA4 0x00 | 设备端返回底层 loader 进度                                   |
| OTA 结束           | 0xA5 0x00 | 设备端主动返回升级成功结束或 app 下发强制停止 OTA            |



## 3、wifi ota流程

### 	1）OTA 开始  

​		连接上wifi socket之后，app发送开始ota命令，并以 json 格式组织 OTA 相关信息填充在data字段

```
// json数据例：
// ble 升级文件， 1006304 Bytes，文件版本 10.1
// wifi 升级文件， 673344 Bytes，文件版本 1.0
{
    "BleFileSize": 1006304,
    "BleFileVerson": 10,
    "BleFileVersonPatch": 1,
    "WifiFileSize": 673344,
    "WifiFileVerson": 1,
    "WifiFileVersonPatch": 0,
}
```

​		设备端收到指令后，检查当前是否可以开始ota。当返回不可开始录音指令时，跟随返回原因，以 1bit 表示一种原因，存在多原因时使用位或组成 1Byte，填充在data字段。当返回可以 OTA 指令时，跟随返回哪颗芯片需要 OTA（版本一致则无需升级，强行推送相同版本的ota文件，无法通过芯片底层loader校验）。当设备返回只需升级其中一颗芯片时，只推送该芯片的 OTA 数据即可。  

```
device->app，data：0x01 0xxx // 可以开始 OTA
```

| 0xxx | 描述                       |
| ---- | -------------------------- |
| 0x01 | Ble 芯片需要升级           |
| 0x02 | Wifi 芯片需要升级          |
| 0x03 | Ble 和 wifi 芯片都需要升级 |

​		

​		当设备端返回不可开始ota时，app通过socket发送关闭wifi指令，设别端会关闭wifi并开启ble。

```
device->app，data：0x00 0xxx // 不可开始 OTA
```

| 0xxx | 描述                                     |
| ---- | ---------------------------------------- |
| 0x01 | 设备存储空间不足                         |
| 0x02 | 电量低于 50%                             |
| 0x04 | 当前正在录音                             |
| 0x08 | flash 繁忙                               |
| 0x10 | 当前正在 OTA                             |
| 0x20 | Ble 和 wifi 芯片与推送版本一致，无需升级 |
| 0x40 | Wifi socket 未连接                       |



### 2）OTA 数据包推送开始  

​	设备返回可以 OTA 后， app 端下发该指令，表明当前推送哪颗芯片的 OTA 数据，设备端返回状态

```
app->device，data：0xxx 
```

| 0xxx | 描述                   |
| ---- | ---------------------- |
| 0x01 | 推送 Ble 芯片升级数据  |
| 0x02 | 推送 Wifi 芯片升级数据 |

```
device->app，data：0xxx 
```

| 0xxx | 描述                                                         |
| ---- | ------------------------------------------------------------ |
| 0x00 | 该芯片无需升级，不进入升级流程，等待需要升级的芯片 OTA 数据开始信号 |
| 0x01 | 芯片进入升级流程                                             |



### 3）OTA 数据包推送  

​	app每秒推送40KB ota数据给设备端，不满40KB的以实际长度为准。设备端接收一帧后，返回该帧的接收状况。

```
app->device：data长度≤40KB
device->app：data长度为1Byte，表明当前帧的接收情况
```

| 1Byte | 描述                     |
| ----- | ------------------------ |
| 0x00  | 接收成功，可以推送下一帧 |
| 0x01  | 帧排序错误               |
| 0x02  | 帧长错误                 |
| 0x04  | CRC 错误                 |
| 0x08  | 数据头尾校验错误         |
| 0x10  | 命令错误                 |



### 4）OTA 数据包推送结束  

​	设备端接收该指令后，判断需要升级的芯片数量与接收完 OTA 数据的芯片数量是否一致，一致则进行下一步，不一致则重复第 2）、 3）、 4） 步继续推送未完成的芯片的 OTA 数据  

```
app->device,data: 0xxx
```

| 0xxx | 描述                  |
| ---- | --------------------- |
| 0x01 | Ble 升级数据推送结束  |
| 0x02 | Wifi 升级数据推送结束 |

```
device->app,data: 0xxx
```

| 0xxx | 描述                                                  |
| ---- | ----------------------------------------------------- |
| 0x00 | 所有 OTA 数据推送完成，进入下一步                     |
| 0x01 | 有芯片尚未完成 OTA 数据推送，重复第 2）、 3）、 4）步 |



### 5）OTA 进度  

​	当第 4 步检测所有芯片 OTA 数据接收完成后，设备主动进入底层 loader，并返回写入进度， 0%~100%（0x00~0x64）， app 无需下发命令。当两颗芯片都需升级时， ble 芯片先升级，wifi芯片后升级，此时设备端会返回两次升级进度。当只有一颗需要升级时，只升级该芯片，只返回一次升级进度。

​	当进度值返回 0xFF 时，表示对应芯片升级失败， 进行下一芯片升级或结束 ota。

```
device->app，data：0xxx 0xxx
```

| 0xxx, 0xxx | 描述                         |
| ---------- | ---------------------------- |
| 0x01, 0xxx | Ble 芯片升级进度(0x00~0x64)  |
| 0x02, 0xxx | wifi 芯片升级进度(0x00~0x64) |
| 0x01, 0xFF | Ble 芯片升级失败             |
| 0x02, 0xFF | wifi 芯片升级失败            |



### 6）OTA结束

​	该命令有两种情况，设备端主动上报和app主动下发

#### 	（1）设备端主动上报

​			所有芯片升级完成后， 设备会关机。关机之前，设备端返回1表示升级成功。

```
device->app，data： 0x01
```

#### 	（2）app主动下发

​			由 app 主动下发该命令，强制停止 OTA 流程，但此强制停止命令，仅在 OTA 进度 命令触发前才有效（进度命令触发后，底层刷写，应用层无控制权限）。 OTA 结束 命令成功执行时，设备端 OTA 流程清空， OTA 文件缓存清空，设备端返回停止指令。  

```
device->app，data： 0x00
```
